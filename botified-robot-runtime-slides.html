Robot-side Runtime Brief

Robot-side
Agent Runtime

Botified 可以理解成机器人本体上的“值班调度层”：它不替代控制器，也不把 LLM 放进实时控制环，而是负责接住用户插话、长任务结果、算法反问和现场状态变化。

常驻服务 单 active loop 异步执行回流 受控网络内运行
one concrete scene

展厅机器人正在带访客参观，导航任务还没结束，用户突然说“先停一下”，视觉脚本又报告“识别失败，要不要重试”。Botified 做的事就是把这些同时发生的事情排好队、写进记录，并让 Agent 做一次高层判断。

Botified robot-side runtime brief
Core Position

机器人 Agent 的难点不是“会不会聊天”，而是现场执行时谁来接住变化。

跨时间

机器人动作通常不是一秒完成。Botified 先把“去 A 点巡检”托管成后台 task，立即返回 task id；等任务完成、失败或超时，再把结果送回 Agent。

跨事件源

用户、脚本、controller、自动化测试都会发事件。Botified 不让它们各说各话，而是统一变成可排序、可回放的输入和 timeline 事件。

跨团队

算法团队继续维护脚本，控制团队继续维护 controller，应用团队只读同一份 state/timeline。Botified 的目标是协调，不是要求大家重写。

field example

真实现场里，问题常常是叠在一起的：讲解动作已经启动，视觉任务突然超时；脚本问“要不要重试”，用户又插话说“先停”。Botified 用队列、任务、回调、反问和事件流把这些事变成一轮轮可解释的决策，而不是把 LLM 长时间卡在一个 tool call 里。

Preserve Existing Workflows

算法脚本先不迁移，也能被 Agent 协调。

已经存在的 Python、C++、shell 脚本不用先改成“Agent 原生工具”。先把它当成一个会运行很久、会成功或失败、会产生日志的后台任务接进来。

0 改造

例如 `python inspect_room.py --area lobby` 继续按命令行跑；Botified 只负责启动、记录 tail、保存 artifact 和 exit code。

低改造

命令被托管成 detached task，返回 `task-1842`。HMI 可以看到 running / timed_out / failed，用户插话时可以尝试 cancel。

按需改造

只有脚本真的需要高层判断时，才输出结构化 request 问 Agent；平时 stdout/stderr 仍然只是日志。

plain language

第一步不是“把算法变成 Agent”，而是“让 Agent 看得见算法在跑什么、跑到哪一步、为什么失败”。看得见之后，才谈更深的交互。

Responsibility Split

LLM 只判断“下一步该怎么做”；真正执行仍由 controller、tool 和安全链路负责。

reason

Botified + LLM：只产生高层意图

例：用户说“带我去会议室”，视觉又说“路线拥堵”。Agent 只决定“改走 B 路线、先提示用户、还是等待 10 秒”。

execute

Controller / Tool：确定执行与反馈

controller 决定具体怎么转身、怎么避障、什么时候拒绝动作；Botified 看到的是 task id、状态、完成/失败/超时原因。

safety

Hardware Safety：独立安全链路

有人按下物理急停时，硬件链路立刻生效。Botified 可以记录并协调后续恢复，但不能替代急停或实时控制。

Single Active Loop

Botified 用一个 active loop，避免机器人同时听从多个高层意图。

01

Input accepted

“去会议室”“任务失败”“脚本反问”先被记录成输入事实。

02

Queue

normal / urgent 都进有限队列；urgent 优先，但不是绕过规则。

03

Drain

runtime 取出当前这一批输入，形成一个 Agent 回合。

04

One turn

同一时刻只让一个 Agent turn 产生“下一步意图”。

05

Commit / rollback

上下文写成功才移除输入；失败就保留，下一轮继续处理。

避免并发高层意图冲突 urgent 仍受队列边界约束 commit 失败可 rollback

例子：机器人正在执行“去会议室”，同时收到“咖啡机旁边有人摔倒”和“视觉脚本询问是否重试”。如果两个 Agent 回合并发输出指令，机器人可能一边继续走、一边准备掉头。单 active loop 把它们收敛成一个明确顺序：先处理 urgent，再决定是否取消原任务。

Long-running Work

长任务不能让 Agent 原地等；它必须有 task id、状态和回流路径。

01 goal

One active turn

Agent 输出“巡检 A 区”，然后释放，不等机器人走完整条路线。

02 start

Detached task

controller / script 启动，runtime 立即返回 `task-42` ack。

03 run

State visible

HMI/TUI 能看到 running、cancelling、timed_out、failed。

04 output

Tail + artifact

日志只保留 tail；图片、轨迹、报告作为 artifact 留下。

05 callback

Delivery state

结果回流可区分 pending、enqueued、delivered、failed。

06 next

Queue drain

Agent 看到结果后继续、追问用户，或选择降级方案。

用户看到的样子

“巡检已开始，任务号 task-42。当前正在 A 区；如果超过 90 秒未完成，会自动报告超时。”

这比“Agent 正在思考/工具正在运行”更适合现场运维。

工程看到的样子

task 有状态机、输出上限、artifact、callback delivery 和 best-effort cancel；失败时能说明是执行失败、回调失败还是超时。

Interactive Stdio

脚本可以“举手提问”，但普通日志不会误触发 Agent。

这页的重点很简单：算法脚本平时照常输出日志；只有打印出明确的 <botified> frame，runtime 才把它当成一个需要 Agent 判断的问题。

  • 本地调试时，脚本仍然可以直接跑，不依赖 Agent。
  • 脚本遇到“继续等、重试、还是失败退出”这种策略问题时，才发 request。
  • Agent 的回答从 stdin 写回脚本，脚本按自己的流程继续。
  • 格式错误、过大、超时的 request 不进入 LLM queue。
  • 每次 request/response 都有 id，方便复盘是哪一次问答出了问题。
<botified>{ "id": "q1", "request": "lidar 未就绪，继续等待还是降级？", "expect": "wait/retry/fail-reason", "urgency": "normal" }</botified> <botified_response>{ "id": "q1", "response": "retry once, then fail with reason" }</botified_response>

例子：雷达未就绪时，脚本不必自己猜业务策略；它只问一次“等、重试还是失败退出”。当前这是 detached background bash 的 opt-in 协议，不是所有工具的默认行为。

Reliability Boundary

用户一句“停下”不能在异常路径里静默丢掉；输入处理必须能证明。

01 accept

Accepted input

先把输入写成事实；写失败就不入队，也不抢断当前 turn。

02 id

Client id

同一个 `client_id` 能区分 duplicate、conflict 和 new input。

03 drain

Pending batch

drain 后先进入待提交批次，避免“处理了一半就丢了”。

04 record

Session record

输入、上下文变更和 timeline 事件写入本地会话记录。

05 commit

Commit

上下文/会话记录确认成功后，才从队列移除输入。

fail

Rollback

provider stop 或 commit 失败时保留输入，fail-closed。

实际例子

用户连续点两次“停止讲解”。第一次已经入队，第二次带同一个 client id 到来，runtime 能判断这是重复请求，而不是生成两次不一致的停止动作。

边界清楚

Botified 追求的是本机 runtime 内的 fail-closed 和可复盘，不承诺分布式 exactly-once，也不把重启后的完整 replay 说成已经解决。

Stop Semantics

“停一下”在机器人现场不是一个动作；Botified 把它拆成四类可观察语义。

urgent

“请马上处理这句话”。它提高调度优先级，让新输入尽快进入下一轮 Agent 判断。

例：用户临时说“别去会议室了，先回前台”。

abort

“别继续想了”。请求中断当前 Agent turn 或 provider 请求边界。

例：Agent 正在生成长计划，现场已经变了。

task_cancel

“正在跑的后台任务尝试取消”。它是 best-effort，因为脚本或 controller 可能已经进入不可取消阶段。

例：巡检脚本还在跑，尝试发 cancel token。

硬件急停

“物理安全立刻生效”。这是独立链路，不由 Botified 或 LLM 替代。

例：按下急停按钮，电机安全链路立即处理。

这页的实际价值是复盘时不再吵“你说的停到底是哪种停”。应用团队看到 urgent，算法团队看到 task_cancel，控制团队看到硬件急停仍独立，大家能用同一份 timeline 对齐事实。

Resource and Cost Guardrails

机器人侧 Agent 要长期在线，不能靠“大家小心点”控制资源和成本。

Queue
消息数量、字节数、HTTP body 都有上限；满了就明确返回 queue full。
Task
每个 task 有 timeout、cancel token、pending request 上限，避免无限挂起。
Output
大日志只保留 tail，完整结果走 artifact，避免把上下文撑爆。
Usage
input、cached input、output、reasoning、total tokens 都进入观测面。

实际例子：机器人站在展厅一天，可能收到几百条状态变化和用户插话。如果没有队列上限、输出上限和 token usage 观测，问题不会立刻表现为“功能坏了”，而是慢慢变成成本失控、上下文污染和现场卡顿。

Deployment Maturity

机器人侧部署要像交付一个本体服务，而不是临时跑一个 demo 脚本。

single binary

  • 服务端是 plain Linux binary，适合放到机器人本体或边缘工控机。
  • 当前 release 路径覆盖 x86_64 与 aarch64，方便开发机和机器人侧对齐。
  • YAML 写普通配置，secret 走环境变量，不把密钥写进配置文件。
  • SHA256 handoff 用于交付验收；install script 属于 release 仓库交付层。
  • 目标形态是复制二进制即可启动，便于小范围灰度和回滚。

controlled surface

  • 工具必须由 config 显式启用；没有启用就不能被 Agent 调用。
  • 非 loopback + tools 需要 service key，避免随便从网络上打进来。
  • bash 是强本地执行器，不是 sandbox；生产环境要谨慎打开。
  • service key 不是 RBAC 或完整 authz，只是最小服务访问门槛。
  • 如果已有控制面负责执行，可以关闭 built-in tools，只保留协调和观测。

实际落地方式：先在开发机用 macOS 路径调试接口，再把同一套配置收敛到 Linux single binary；现场灰度时只打开试点所需工具，其他执行面保持关闭。

Pilot Request

建议先做三个很窄的试点，不要一上来做“大平台迁移”。

算法团队

  • 选 2 个现有 CLI/脚本：例如巡检脚本和视觉识别脚本。
  • 一个只做 detached task，看状态、超时和 artifact。
  • 一个增加 <botified> request / response，验证脚本能向 Agent 反问。
  • 产物：接入样例、失败/超时日志、一次脚本反问记录。

应用团队

  • 用 `/v1/state` 做最小状态面板：当前在跑什么、卡在哪里。
  • 用 `/v1/timeline` 做现场事件视图：用户输入、任务回调、失败原因。
  • 保留 curl 可复现路径，关键流程不用依赖 UI 手点。
  • 产物：state 面板、timeline 视图、三条 curl 验收命令。

控制团队

  • 定义 3-5 个 controller action 边界：如导航、讲解、等待、取消。
  • 确认 LLM 不进入实时控制环，不发关节级命令。
  • 状态切换和硬件安全链路保持独立。
  • 产物：action 边界表、stop 语义表、急停不由 Botified 替代的说明。

共同验收样例：发起“去 A 区巡检”，中途插话“先停一下”，脚本询问“是否重试识别”，最后从 timeline 里看到输入、task、request、cancel/timeout 和恢复策略的完整链路。
