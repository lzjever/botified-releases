Robot-side Agent Runtime

Botified 技术主张

Botified 的原创性不在某一个单点 API，而在一组面向机器人本体执行的组合设计：把多源输入、后台任务、运行中反问、可靠队列、可观测事实和模型成本收敛到一个常驻 runtime 契约中。

Overview

先建立阅读坐标

下面四块把长文的核心定位、接入方式、runtime 契约和工程成熟度先压缩到一屏，后续章节保留完整细节。

Core Position

Botified 是机器人本体侧或受控控制网络内的常驻 runtime，不是 chat-first 应用。它处理多源事件、排队、后台任务、状态和结果回流。

Access Cost

最低接入不是写插件。非交互 CLI、脚本、本地命令和 curl 调试方式可以继续保留；interactive stdio 只在执行期确实需要 Agent 判断时 opt-in。

Runtime Contract

核心契约包括单 active loop、统一输入队列、detached task、callback、cancel、tail/artifact、/v1/state 和 /v1/timeline。

Engineering Maturity

single binary、x86_64 / aarch64、botified-tui 自举经验、provider usage / cached token / reasoning token 和成本观测共同构成交付基础。

Access Model

最低接入心智负担

接入路径面向算法、应用和本体服务已有工作流设计，先托管、再交互、最后沉淀 skill。

Botified 的最低接入成本不是“写插件/写技能”。非交互 CLI、脚本、本地命令可以保持现有 argv、env、cwd、stdout、stderr、exit code、shell pipeline 和 curl 调试方式，由 Botified 托管进程生命周期、tail、artifact、callback、cancel 和 timeline。只有当程序确实需要在执行期请求上层判断时，才选择性增加一个 stdout request envelope 和一个 stdin response envelope：打印 <botified>{...}</botified>，读取 <botified_response>{...}</botified_response>。不要求 SDK，不要求把算法模块改成 server，也不要求先迁移到复杂插件生态或配合写SKILL。

接入梯度

0 改造：普通 CLI 先作为 task 被托管，获得 tail、artifact、exit code 和 timeline。
低改造：detached task 获得 task id、cancel、callback 和状态观测。
按需改造：interactive stdio 用 <botified> / <botified_response> 处理运行中反问。
Engineering Evidence

成熟度工程证据

工程证据原文完整保留，并用三张卡片分别呈现交付、自举和成本性能。

交付形态足够轻：single binary，复制即可运行

Botified 服务端以单文件二进制交付，对使用者来说不需要 Python、Node、Rust toolchain、容器镜像或额外包管理流程；把二进制复制到目标机器即可执行。当前发布链路覆盖 Linux x86_64 和 Linux aarch64/ARM64，适配普通开发机、服务器和机器人侧 ARM 运行环境；macOS 版本正在补齐。发布仓库提供在线安装脚本，自动识别架构、下载对应二进制并校验 SHA256，开发和部署都可以用同一条路径。

Botified 已经用自身能力完成过高复杂度自举开发

botified-tui 本身就是一次很好的技术证据：它不是一个简单 demo，而是包含 HTTP client、timeline follow、state bootstrap、task dock、输入模型、调试视图和大量测试的独立 TUI 客户端。内部开发中，botified-tui 基本由 Botified 配合 LLMUP + GPT-5.5 在约 72 小时内无人值守完成，说明 Botified 不只适合机器人，也具备通用智能体需要的长期任务推进、代码修改、测试反馈、错误恢复和工程闭环能力。

性能与成本不是事后优化，而是 gate

Botified 把 provider usage、cached input tokens、reasoning tokens、turn completed usage、context compaction 和 prompt 稳定性放进运行时和测试视图中，并把 KV cache hit rate 与 cost efficiency 纳入严格性能 gate。对机器人本体执行来说，这一点很关键：本体侧 Agent 需要长期在线，性能波动和 token 成本会直接影响响应速度、部署规模和实际可用性。

Claims 1-8

机器人侧 runtime 定位

确立 Botified 的机器人本体侧 runtime 定位：多源事件、统一队列、职责分层和 controller 边界。

01 Botified 的基本抽象是机器人侧常驻 runtime，而不是 chat-first 应用 detached taskcontroller

技术重点不是“用户说一句，Agent 回一句”，而是服务长期运行后如何接收多源事件、排队、触发 Agent activation、托管后台任务、记录状态并把结果重新带回决策链路。机器人本体不会像网页请求一样一次性结束，动作执行、传感器准备、算法推理、控制切换和人工插话都可能跨越多个时间窗口。把 Botified 放在 robot-side runtime 位置，可以让这些时间窗口拥有统一的输入、任务和观测模型，而不是散落在每个 demo 脚本里。

Boundary不是“用户说一句，Agent 回一句”，而是服务长期运行后如何接收多源事件、排队、触发 Agent activation、托管后台任务、记录状态并把结果重新带回决策链路。
02 Botified 采用 agent-centered activation，而不是 user-input centered interaction queuedetached taskcallbackcontroller

用户消息只是 activation event 的一种，后台任务完成、任务失败、脚本运行中发出的 task request，也可以成为 Agent 被唤醒的原因。控制面或本体服务的事件需要先经 /v1/messages、task callback 或 task request 适配后进入统一队列，而不是直接绕过 runtime。这个方向对机器人尤其关键，因为现场关键事件经常不是由用户主动说出来的，而是由本体服务、算法模块或执行状态变化产生。

Boundary不是直接绕过 runtime。
03 单 active agent loop 是机器人高层决策的收敛点 single active loopqueuecontroller

机器人本体执行不适合多个高层 Agent 回合同时向 controller 发出互相冲突的意图。Botified 的服务端队列和单 active loop 使同一时刻只运行一个 Agent 回合，其他输入进入队列并在边界处被处理。这个设计不是为了降低并发能力，而是为了把机器人高层意图收敛到可推理、可排序、可中断的序列中，降低“两个脑子同时控制一个身体”的风险。

Boundary不是为了降低并发能力，而是为了把机器人高层意图收敛到可推理、可排序、可中断的序列中，降低“两个脑子同时控制一个身体”的风险。
04 统一输入队列让用户插话、任务回调和模块请求共享调度语义 queuedetached taskcallbacktimeline

如果用户输入走聊天通道、后台任务走日志通道、算法模块走自定义回调通道，机器人现场行为会很难解释。Botified 的 queued message 带有 source、urgency、metadata 和 cursor，使不同来源的输入进入同一排队模型。这样应用同事和算法同事讨论问题时可以对齐在“哪个输入被 accepted、哪个输入在队列中、哪个输入被 drain、哪个输入触发了 Agent 回合”这些事实上，而不是各看各的日志。

Boundary不是各看各的日志。
05 在工具和 controller 侧按职责拆分时，LLM 可以被限制在高层 reasoning 和规划层 controllersafetylimits

Botified 本身提供 Agent runtime、tool 调用、任务托管和事件调度；底层运动参数是否暴露，取决于工具和 controller 如何设计。推荐架构是让 LLM 理解目标、选择策略、处理上下文、判断是否需要追问或降级，而把确定性命令、状态切换、任务取消和安全链路交给 controller/tool。这个分层能让算法、本体和控制同事接受 Agent 接入，因为它不要求他们把实时控制权交给模型。

06 决策和执行解耦后，Agent 不必为低频控制动作长时间阻塞 controller

人型机器人动作、讲解、抓取准备、感知检查和状态切换往往是低频但耗时的执行过程。Botified 适合把这些过程 post 给 controller 或本体服务，让 controller 负责执行状态推进，Agent 只在需要判断、确认、切换或恢复时被唤醒。这样能够把“持续执行”从“持续占用 Agent main loop”中拆开，使 Botified 更快响应用户插话和后台事件。

07 urgent、abort、task_cancel 和硬件急停被明确区分 detached taskurgentcontrollersafety

机器人系统里“停一下”可能意味着停止当前 Agent 回合、取消一个后台任务、切换 controller 状态，或者触发硬件急停。Botified 把 urgent 定义为调度提示，把 abort 定义为 Agent 回合边界的中断，把 task cancel 定义为后台任务取消尝试，并明确不替代硬件急停。这个语义分层能避免把不同层级的 stop 语义混在同一事件上，让每一层都有自己的责任、失败模式和可观测结果。

Boundary不替代硬件急停。
08 Botified 的 runtime 边界适合与 agentic-robot-controller 组合，而不是替代 controller callbackcontrollersafety

controller 更适合处理低频控制、状态切换、动作状态保持和本体服务编排；Botified 更适合处理多源事件、用户语言、skill 规程、异步任务和高层决策。二者通过窄接口组合时，Botified 不需要进入实时控制环，controller 也不需要理解复杂对话上下文。更准确的分工是：controller 保持确定状态机和动作约束，Botified 补充语言、上下文、回调和 task request 触发的高层决策。

Claims 9-18

后台化长任务与异步事件回流

把动作、视觉、音频、地图和脚本执行从同步 tool call 中拆出来，成为可观测、可取消、可回流的任务对象。

09 detached background task 是一等运行时对象 detached taskcallbackcontrollerlimits

机器人动作、视觉处理、音频分析、地图更新和长时间脚本执行都不应被压缩成一次同步 tool call。Botified 允许工具调用在后台 detach，返回 task id，并在 task registry 中保留状态、输出、artifact 和取消令牌。这样长任务从“聊天记录中的一段输出”升级为可被观测、等待、取消和回调的 runtime 对象。

Boundary不应被压缩成一次同步 tool call。
10 detach ack 明确表示“已托管运行”，不伪装成任务完成 detached taskcallbacklimits

Botified 的 detached ack 会说明 background task detached、status running、task id、timeout 和后续 callback，而不是把异步启动包装成最终成功。机器人场景中这个边界很重要：动作开始执行不等于动作完成，导航开始不等于到达，感知任务启动不等于识别结果可信。把 ack 和 final result 分离，可以减少 Agent、UI 和现场人员对执行进度的误判。

Boundary不是把异步启动包装成最终成功。
11 后台任务终态通过 callback 尝试回到 Agent，形成闭环决策 queuedetached taskcallbackdurable

detached task 完成、失败、超时或取消后，会生成 task callback，并在条件允许时重新进入服务队列触发后续 Agent 处理；该路径仍受 queue full、shutdown、持久化失败和进程退出等边界影响。对机器人来说，这意味着“执行结果”可以回到高层 reasoning 链路，比如动作失败后切换策略、识别失败后请求用户补充、控制命令超时后进入降级路径。它不是必达消息系统，但已经比单纯写日志更适合机器人长任务。

Boundary不是必达消息系统，但已经比单纯写日志更适合机器人长任务。
12 callback delivery 具备 Pending、Enqueued、Delivered、Failed 等状态，而不是一次性丢给队列 queuedetached taskcallbackurgent

机器人现场队列可能满、Agent 可能正在处理 urgent 输入、服务可能处在 shutdown 边界。Botified 将 callback delivery 建模为状态机，并在队列压力下保留 pending 状态，待条件允许再重试入队。这个机制让后台任务结果不至于因为一时队列不可用就消失，也让调试工具可以看见结果为什么还没有被 Agent 消费。

13 任务生命周期覆盖主要终态，并为异常状态预留表达空间 controllerlimits

机器人任务的失败模式多，不应只用“成功/失败”二值表示。Botified 的强证据覆盖 running、completed、failed、timed_out、cancelling、cancelled 等状态，状态模型中也预留了 lost 这类异常表达。这个细粒度状态对控制台、HMI 和远程支持有实际意义，因为不同状态对应不同处理方式：等待、重试、查看 artifact、取消、重新发起或要求人工介入。

Boundary不应只用“成功/失败”二值表示。
14 大输出通过 tail 和 artifact 管理，避免污染模型上下文 costlimits

算法模块和本体脚本会打印大量日志、诊断信息、图片路径或中间结果。如果这些输出全部进入 LLM 上下文，会增加成本、降低可靠性，还可能让模型被无关日志误导。Botified 使用 bounded tail 和 capped artifact 处理任务输出，给 Agent 和人类足够的摘要，同时把完整输出保留在受控大小范围内用于调试。

15 超时和取消是后台执行的工程护栏 detached taskcostcontrollersafety

Botified 的工具执行有默认 timeout、可配置 timeout、detached task 终止时间和 cancellation token。取消在进程层面仍是 best effort，不应包装成功能安全保证，但它已经把“长任务永远挂住 Agent 或资源”的风险收敛到了 runtime 控制范围内。机器人侧任务天然可能遇到设备未准备、驱动阻塞、网络等待，超时和取消边界是从 demo 走向长期运行的基础。

Boundary不应包装成功能安全保证，但它已经把“长任务永远挂住 Agent 或资源”的风险收敛到了 runtime 控制范围内。
16 并发上限和队列压力被显式建模 queuedetached taskcontrollerlimits

Botified 对队列长度、队列字节、后台任务并发、pending task request 数量都有上限或配置边界。机器人系统中，资源比云端服务更紧张，CPU、内存、传感器、设备句柄和控制通道都可能成为瓶颈。把这些压力点放进 runtime，而不是让每个脚本各自处理，可以降低 runaway 任务拖垮整机交互的概率。

Boundary不是让每个脚本各自处理，可以降低 runaway 任务拖垮整机交互的概率。
17 shutdown 有有限 quiescence 边界，避免半提交被默默忽略 detached taskcontrollerlimits

机器人本体服务经常会被 systemd、调试脚本或控制面重启。Botified 在 shutdown 时会尝试取消后台任务、等待关键路径收敛，并保留已 accepted 的输入语义。这里不能夸大成“恢复所有物理任务”或“进程死亡后恢复后台任务”，但它至少把服务重启时常见的输入半提交、任务取消和状态不可见问题纳入了运行时设计。

Boundary不能夸大成“恢复所有物理任务”或“进程死亡后恢复后台任务”，但它至少把服务重启时常见的输入半提交、任务取消和状态不可见问题纳入了运行时设计。
18 后台化长任务和异步事件回流让 Agent main loop 少被执行等待占用 queuedetached taskcallbackurgent

Botified 不是硬实时异步调度框架，provider 调用、inline tool 和持久化路径仍可能占用当前回合。它的关键价值是通过 detached task、callback、task request 和队列，把可后台化的执行等待转移给 runtime 和 controller，把 Agent 留给新的用户输入、urgent 调度、策略判断和任务结果处理。用户不会总是等机器人完整执行完一个动作才说下一句话，因此这个服务模型更贴近机器人现场交互。

Boundary不是硬实时异步调度框架，provider 调用、inline tool 和持久化路径仍可能占用当前回合。
C

Claims 19-29

交互式 stdio 与低心智接入

让算法模块继续按 CLI/stdio 工作，只在需要高层判断时显式请求 Agent，降低接入和调试成本。

19 Botified 让 Agent 适配现有 CLI/脚本开发方式，而不是要求算法模块适配 Agent 框架 callbackcostsingle binary

算法同事通常已经有 Python、C++、shell、ROS bridge 或本地二进制，可以在终端独立运行和调试。非交互脚本可以保留 argv、env、cwd、stdout、stderr、exit code 和现有 shell pipeline；Botified 只是在外层托管进程生命周期、tail、artifact、callback 和 cancel。这个接入路径降低了算法模块适配成本，因为它不要求一开始就改造成复杂插件、HTTP 服务或 SDK。

20 interactive_stdio 是显式 opt-in，降低旧脚本误接入风险 detached taskstdiocontroller

目前 interactive stdio 只对 bash tool 生效，并且面向 detached background task；开启后任务会进入后台托管路径，避免脚本等待 stdin 时占住 Agent 回合。普通任务的 stdout/stderr 仍按输出处理，只有显式开启后 Botified 才解析 <botified>...</botified> frame。这种 opt-in 设计适合机器人内部渐进接入：已有脚本可以先作为普通命令运行，只有需要运行中请求 Agent 判断的模块才开启交互协议。

21 <botified> frame 把“脚本运行中反问 Agent”做成小而硬的协议 stdiolimits

一个算法模块遇到不确定情况时，可以向 stdout 写出形如 <botified>{"id":"q1","request":"...","expect":"yes/no","urgency":"normal"}</botified> 的结构化请求，再从 stdin 读取 <botified_response>{...}</botified_response>。协议字段保持有限：id、request、expect、timeout_secs、urgency，未知字段拒绝。不交互的脚本完全不需要增加这两行；需要交互的脚本也不必改造成完整 Agent client。

22 普通 stdout/stderr 不会变成伪指令 queuestdiourgent

机器人算法日志里可能有大量“error”“warning”“retry”“stop”等词，如果这些文本默认进入 LLM 队列，会产生误触发和提示注入风险。Botified 明确规定 plain stdout/stderr 只是 task output，不会在任务运行中唤醒 Agent；只有显式 <botified> frame 才是 task request。这个边界让算法同事保留原有日志习惯，同时把 Agent 交互入口收窄到可审查协议。

23 task_reply 由 Agent 写回 child stdin，算法脚本读取结构化响应帧即可继续 stdiocontroller

task request 进入 Agent 后，Agent 可以结合用户目标、skill、当前上下文和系统状态做判断，再通过内置 task_reply tool 写回 <botified_response>...</botified_response>。脚本侧只需要从 stdin 读取响应或异常 envelope。人工 manual reply 适合 debug 和 break-glass，不应成为正常路径；正常链路应保持由 Agent 通过 task_reply 响应。

Boundary不应成为正常路径；
24 admission 失败请求不会进入 LLM transcript，并尽量返回结构化 exception queuecostlimits

Botified 对 frame JSON、字段白名单、request 大小、id token、expect 大小、timeout 合法性都有校验。无效、超限、未知字段等 admission 失败请求不会进入 LLM 队列；如果能识别 request id 且 stdin 可写，则向子进程返回 bounded exception frame。已 accepted 但过期或终止的 pending request 会被清理并记录，late reply 不应再写回子进程。

运行中的脚本可以请求 Agent 判断，但不能无限堆积问题。Botified 对单 task pending request、全局 pending request、默认 pending timeout、请求文本大小和回复大小设边界。机器人现场必须这样设计，因为一个异常脚本不应把 Agent main loop 拖进无界问答，也不应通过大量请求挤占用户插话和安全相关输入的处理空间。

Boundary不能无限堆积问题。
26 expect 是语义提示，不是强 schema，降低算法模块协议负担 cost

很多机器人判断无法提前做成完整 JSON schema，例如“是否继续等待 lidar”“是否让用户再说一遍”“是否重试动作生成”。Botified 的 expect 只是给 Agent 的语义提示，例如 yes/no 或 fail-reason，而不是要求算法同事设计复杂 schema。这样既保留结构化边界，又降低早期接入和实验阶段的协议成本。

Boundary不是要求算法同事设计复杂 schema。
27 算法程序可以脱离 Agent 独立调试，接入后再获得 Agent 协调 stdio

一个 CLI 程序可以先在终端中用人工 stdin/stdout 模拟交互，确认算法逻辑正确后，再由 Botified 托管为 interactive stdio 任务。需要复现交互路径时，开发者可以直接运行脚本，手工输入一行 response envelope；不需要先启动完整 Agent 栈。这个路径对机器人研发很现实，因为算法模块常需要单独跑数据、接传感器、复现日志、验证边界条件。

28 manual reply 适合 debug 和 break-glass，不应成为正常链路 stdio

Botified 保留手动回复 task request 的能力，方便开发、现场排障和紧急验证。但正常路径应由 Agent 通过 task_reply 响应，保持 task request、Agent 判断、skill 约束和上下文一致。这个边界能让应用同事放心：调试工具存在，但运行时主链路不会变成绕过 Agent 的隐式人工通道。

29 标准 HTTP 和 curl 让应用侧自动化不必绑定专用 UI timelinestateurgentcontroller

/healthz、/v1/state、/v1/messages、/v1/timeline、/v1/abort 等接口可以直接用 curl、HMI、测试脚本或控制台调用。TUI 是服务附着式客户端，不是第二套控制面。对应用团队来说，这意味着他们可以用熟悉的脚本自动化方式接入 Botified，不需要等专用前端或私有调试工具才能开始集成。

Boundary不是第二套控制面。

Claims 30-38

高可靠调度与恢复边界

把输入 accepted、队列 drain、commit/rollback、urgent 和 stale request 都纳入可靠调度边界。

32 队列处理有 drain、commit、rollback 的事务边界 queuecallbackdurable

Agent 回合从队列 drain 输入时，Botified 会形成 pending batch，并在 provider/context 持久化成功后再 commit；失败时可以 rollback，让队列消息不因中间错误被静默移除。机器人场景中，用户插话和任务回调丢失会直接影响现场行为。这个队列边界比简单 FIFO pop 更可靠，因为它把“拿出来处理”和“确认处理成功”拆成了两个阶段。

33 urgent-first drain 在有限队列内支持优先处理急迫输入，同时保留 rollback 语义 queueurgentdurablecontroller

Botified 会在 drain 时优先选择 urgent 输入，再处理 normal 输入；但 urgent 仍受队列上限、pending limit、provider/tool cancellation 和 timeout 约束。这个设计适合机器人，因为用户插话或高优先级 task request 需要尽快进入高层决策，同时又不能绕开 runtime 的所有工程护栏。

34 持久化失败时不触发抢断，避免系统进入“未记录但已改变”的状态 urgentdurable

对 urgent 输入而言，最危险的情况是还没有可靠记录，就已经打断当前 Agent 回合。Botified 的顺序是 accepted input 持久化成功后才进入后续入队和抢断逻辑；若持久化失败，则返回 rejection 而不是改变运行状态。这个边界体现的是工程可靠性：宁可明确拒绝，也不制造无法复盘的隐式状态变化。

Boundary不是改变运行状态。
35 stale task request 会在进入 provider 前被清理，避免过期问题继续影响 reasoning state
